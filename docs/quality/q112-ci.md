## F1 (high) Editor drops a selection made right after it gets the focus
- Repro: open a note, focus the editor and select text at once while the main thread is busy
  (e2e 210 busy-waits 60 ms after selecting): selection collapses to the cursor; Ctrl+J opens the
  assistant instead of the inline AI bar. Without the busy wait it depends on load (16/170 on CI).
- Root cause: prosemirror-view `handlers.focus` restores the state's selection 20 ms after focus
  when the DOM selection differs from the last one it read. WebKit reports the new DOM selection with
  a late `selectionchange` (12-59 ms measured locally, later under load). Probe log: focus timer ran
  docView.setSelection(1-1) -> Selection.collapse, then `selectionchange ""`.
- Fix: ui/src/editor/focusSelection.ts (FocusSelection extension, in buildExtensions): its focus
  handler runs before ProseMirror's and reads the DOM selection (DOMObserver.flush) at the same 20 ms,
  so the restore finds nothing to do.
- Tests: vitest focusSelection.test.ts (holds selectionchange back like WebKit; with the extension
  kept, without it lost); e2e 210 fails without the fix ("the selection is kept"), passes with it.
  170's workaround (re-select until it holds, 9ef5893) removed.

## F2 (high, CI) Every app start took ~30 s on CI; a 5 s freeze right after start
- Reproduced locally with a session bus whose org.freedesktop.portal.Desktop activation never
  completes (as a portal unit that cannot start on the runner's user bus): launch 31.9 s (CI 31.3 s).
  Startup timing (new ANNALO_STARTUP_TIMING log): setup after 25057 ms (GtkApplication startup:
  StartServiceByName portal.Desktop, dbus-daemon service_start_timeout 25 s), main window after
  30450 ms (tao portal::theme Read, 5 s timeout, gdb stack: tao::platform::portal::theme <-
  Window::new <- create_main_window). 1.5 s after the first frame the capture popup is precreated:
  a further 5 s portal Read on the main thread, which froze the UI exactly when the first test of a
  file ran its 5 s waits -> the ~37 s failures (55 "not saved" etc.).
- Not an app bug (GTK and tao block on a broken desktop portal; on a working desktop both answer at
  once). Disabling tauri's `dbus` feature would remove the 5 s reads but also dark-mode following
  on GNOME, so kept.
- Fix (harness): every test file's apps get a private dbus-daemon session bus without services
  (DBUS_SESSION_BUS_ADDRESS set, so no runner user bus and no X11 autolaunch). Same desktop as a
  dev machine without a bus, which the tests expect (135/136/137 check the secrets.json fallback,
  so a gnome-keyring would break them). Launch with the broken bus on the machine: 1.7-1.9 s.
- The harness prints the app's startup timing when a start takes > 10 s.

## F3 (medium, CI) Chrome left running on the test display
- 28-quick-links right-clicks ribbon links; WebKitWebDriver's right click sends mouseup/click with
  button 0, so the link opened: xdg-open https://jira.firma.de/browse/AET and /home/user/Projekte.
  On the runner that started Chrome (orphan at job end). Real right clicks in WebKitGTK fire no click.
- Fix (harness): `xdg-open` (and BROWSER) is a script that records its arguments; app.opened()
  returns them, close() prints "[e2e] handed to xdg-open, not started: ...".
